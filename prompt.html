AI 产品经理课程笔记：提示词工程

2026-11-26 课堂 · 录音原文要义（转写有错字，专有名词已按常识校正）

核心要点

  • 跟 AI 说的每一句话都是提示词（User Prompt，自然语言）。之所以还要叫“提示词工程”，是因为只丢一句模糊指令（如“帮我分析小红书”“生成一只兔子警官”），结果往往不可用；表达本身也有局限（课上称作“舌尖效应”：脑子里有画面，却说不准）。要拿到可直接用的交付物，必须把需求、角色、上下文、格式和示例写清楚。
  • 三类提示词走不同通道：User Prompt 及时、任务驱动、依赖上下文，窗口满了会被顶掉；System Prompt 走单独通道，每次回答前先读，不会被顶出，宜短，且必须写清工作流；Meta Prompt 由模型厂商预置，用户改不了，规定安全边界和默认语气。
  • 指令大致按梯度遵循：平台 / Meta Prompt（禁涉政涉黄涉暴等）＞ 开发者 System Prompt ＞ 用户 User Prompt ＞ 联网搜索等外部内容 / 上下文。是否稳定，取决于提示词质量和模型能力；同一模型，提示词功力可以明显拉高可用智力。
  • 写 Agent 系统提示词的常用技法：用 Markdown 分层并加粗提权；给不确定对象起名以便双向引用；把固定话术用引号钉死；穷尽用户各种不完整输入并给出兜底；通过公司 Tool List 用工具名调用封装好的能力，不要把 API Key 写进提示词。
  • 提示词没有唯一模板，最终看输出质量和稳定性。它会随模型升级过时，必须做版本管理；提示词微调已从 2024–2025 年的“必备技能”变成现在的“基础技能”。新手套框架可以，但工作流建议必留。
  • 知识库（RAG）本节只点到用法：切块不能太碎也不能太长；Embedding 做向量化，Rerank 按相关度二次排序。课上提到，不少企业已不再用当年那种 RAG，或已换成其他形态，但面试回顾 2024–2025 年经历时仍可能问到，所以还要学。
  • 当晚作业与安排：把 Dify Web 应用链接放到笔记最上方；交课堂笔记；拆解老师提供的系统提示词（务必创建副本再评论）；准备次日上午辩论。API / Tool / MCP 原计划下午讲，因与 Agent 拆不开，推迟到一起讲。

一、先有一个能正常对话的 AI：付费与模型分工

  • 课前强调：手里先要有一个能正常对话的 AI。讲师更看好 Google 生态的打通程度——订阅后可联动多项工具与平台，包括前一天讲过的 Notebook（NotebookLM 一类）。同一生态里还有 Antigravity（课上也称“反重力”）：Google 的 Agent，对标 Anthropic 的 Claude Code、OpenAI 的 Codex，本质是一套 Agent Harness。讲师认为 Antigravity 这套 Harness 目前并不突出，甚至可能不如 DeepSeek 的 Harness，但其中性价比高的模型质量仍不错，档位上被类比为 Claude Opus 系列。
  • 档位建议：若付费，买 Pro 即可；Plus 不够用——额度不足，且用不上当时各平台和 X（Twitter）上在推的那两款更强模型。Antigravity 还可能受地区限制（转写提到需转到美国才好用）；Gemini 与 Antigravity 是不同客户端，不必绑死在后者上。自己开通官方订阅通常至少需要 Visa，在国内付款可能遇到“不支持所在国家”一类提示。讲师说课上先不占用时间，谁找到相对靠谱的购买渠道可以事后在群里同步；讲师自己则打算先充 Ultra 试试模型。
  • 三家要搭配用，不要只钉一家。文案、方案、视频脚本一类工作可交给 Gemini，讲师认为文本甚至可能强过 Claude；写代码仍交给 Codex；Claude 若跑通，再切过去用。每家都有短板和长处，只认准一个，其他场景往往会“特别凑合”。后续开发主路径仍看 Codex。

二、什么是提示词，为什么还要叫“工程”

  • 今天的新内容是 提示词工程。昨天在 Dify 左上角已经试过一次，那就是提示词。日常跟 AI 说的每一句话都算 User Prompt，但“工程”的意义在于：同一句话的清晰程度，会直接决定结果能不能用。
  • 反例一（生图）：只说“生成一只兔子”，或再加上“穿着警服”，很难得到朱迪那样的兔子警官。原因有二：表述能力有限；审美和设计领域有大量难以用自然语言说清的感觉，往往还要靠参考图和专业词汇。
  • 反例二（竞品分析）：对产品经理常做的事，只说“帮我分析一下小红书”，模型很容易吐出往年数据、指标甚至财报，对“要做一款类似产品”几乎没有帮助。真正可能有用的是用户画像、使用场景、前端 UI 与交互等，但若不说明白，模型无法对齐。接着就要多轮拉扯，结果仍然是有的能用、有的不能用。
  • 学完本节后，做竞品分析应能用 一段提示词 直接得到可用结构，例如：表格化的功能拆解、核心用户与场景、解决的问题，以及重点启发或方案提示。

三、三类提示词：User、System、Meta

1. 对照总览

类型谁来写 / 谁能改要点
User Prompt
用户提示词		用户在输入框里发出的指令及时性、任务驱动、强依赖上下文；与模型输出、思考过程一起计入窗口额度，超限会被顶出并遗忘。
System Prompt
系统提示词		开发者，或开放了自定义指令 / GPTs 一类入口的用户单独通道，相当于窗口顶部锚定的设定；每次回答前先读，不会被聊天记录顶出去。宜短。
Meta Prompt
元提示词 / 厂商提示词		模型厂商预置，用户通常接触不到规定安全边界和默认回复语气、排版习惯；优先级高于用户和开发者的设定，无法被普通系统提示词覆盖。

2. 上下文窗口、记忆与 Agent Harness

  • 普通对话页只有一个输入框。发得越多，越容易碰到 上下文限制。课上举例：某模型当前窗口可能是 128K，超了之后更早的内容会被顶出去。以前检验窗口是否已满的取巧办法，是先约定“以后每次都叫我老大”；一旦不再这么叫，说明前面的规则可能已被顶掉。这是在还没有较成体系的 Memory 时常用的观察方法。
  • Grok Bot 被课上定义为 Personal Agent：底层有单独的记忆模块，消息往往不能撤回，发出去的内容会沉淀为记忆，像跟一个人聊天，不可能把刚说的话从对方脑子里拽出来。豆包、DeepSeek 等应用端 / 网页端，仍更容易遇到窗口被顶满的问题。
  • Grok Bot、Codex、Claude Code 这一类属于 Agent Harness。它们一般带记忆机制，常把文件存在本地，但 并非没有上下文限制。超限时会把先前对话做一次压缩（类似记笔记而不是存逐字稿），再写入记忆库，用来节约窗口。讲师把“在一个窗口里设定的规则，新开窗口就失效”称为 窗口效应：普通模型会话之间往往不通；现在接触的这类 Agent 才更可能有一定互通。
  • 计算额度时，用户输入（input）、模型输出（output），以及中间的 thinking，都会算进上下文。这些内容在数据层面走同一通道，再交给大模型。

3. System Prompt：单独通道，每次先读

  • 昨天 Dify 左上角的大段设定（如“猫粮”案例、猫猫娘口吻），就是 System Prompt。模型每次先看设定，再看用户问题，这个动作会重复发生。
  • 课上用机器人类比：打开后背开关，写入“从现在起你是我的厨师”，这句是系统提示词；之后说“我想吃番茄炒蛋”，才是用户提示词。机器人接到指令不会立刻执行，而是先核对身份和任务。若把设定改成园丁，再让它做饭，它应拒绝并去打理花园。
  • 可视化理解：系统提示词像钉在窗口顶部的锚定模块，下面的聊天再长，这块内容也 始终留在窗口内、不会被顶出，因此和用户对话走的不是同一条数据通道。

4. Meta Prompt、防护与攻防（只记概念）

  • 还有一类用户通常接触不到的词，课上称为 Meta Prompt（也说成厂商 / 开发侧的底层提示词）。继续用机器人类比：厂商会在出厂前把不可逾越的边界写死（课上类比为“机器人三大定律”），用户的系统设定覆盖不了。今天使用的模型也不是“原版裸模型”，厂商会先包一层 防护机制，钉死边界。这也是付费用户仍无法让模型协助违法事项的原因。
  • 业内把用提示词手段诱导模型做本来不该做的事称为 “越狱”。早期模型能力较弱时更容易被绕过；厂商同步升级防护，两边形成 攻防，大约从 2024 年持续至今。课上明确：攻防提示词与本课主线无关，只需知道存在这件事，而且主要靠提示词而不是攻击脚本。
  • 开发者实际能改的只有两块：User Prompt 和 System Prompt。纯用户视角往往只有输入框（如 Grok Bot）；到了公司或 Agent 编排平台，才有开发者视角，才能写系统提示词。

5. 谁先把 System Prompt 入口开放给普通用户

  • 讲师提到，把 System Prompt 入口开放给 ToC 用户，较早的是 OpenAI 的 GPTs（“我的 GPT”）：左边写系统提示词，右边做测试。这种右侧可直接试结果的环境，称为 沙盒测试（类比古代营帐里的沙盘推演）。后来产品形态又改成“插件”等概念。ChatGPT 的自定义指令、Codex 的编辑入口（转写里还出现 AGENTS.md）也属于同类能力。
  • 系统提示词还分 全局 和 项目级。以 Codex 为例：在全局指令里写入“以后只叫我老大”，则桌面端和网页端、任意项目，回答前都会先读这条。也可以只对某个文件夹 / 项目生效；换一个新项目就不再遵循。后面做开发会大量用到这两级。
  • 系统提示词要尽量控长度，不要写太长。每次对话模型都会先通读一遍。若写了三千字，用户只发一句“你好”，也要先消耗这些 token。全局里放一些写作习惯一类的轻量约定即可。

四、User Prompt：定义、案例与生图练习

1. 记住三个词

  • 若只记定义，记住：及时性、任务驱动、上下文依赖。发出去会当下遵循，但聊得越多可能逐渐遗忘；“给我做一个文档 / PPT / 系统”属于任务型；回答时一般会回看上文——例如先说“写一个文档”，再说“调研小红书”，模型得自己拼出“这是一份小红书竞品分析”。多轮对话必须依赖上下文，不能像“七秒记忆”。

2. 面试话术：从通用模板到可直接念的稿

  • 坏例子：只问“面试官问我为什么从上家离职，怎么回？”模型可能给出若干模板化段落（“了解到贵公司在某某方向的布局，非常契合……”），还要自己再改，不好直接用。
  • 好例子应写清：场景（被问到某题，需要口语化话术）、信息补充、以及约束——语气自然真实，不要“首先 / 其次 / 然后”的八股，不要“与贵公司高度吻合”套话；话术清晰得体，控制在 150 字以内；只输出参考话术，禁止额外分析或解释（避免模型再补“您还满意吗”一类尾巴）；并预留“若与预期有偏差，按用户最新指令微调，循环到满意”。这样换一道题时，往往只需替换“面试问题”和“信息补充”，其余可复用。

3. 生图提示词：结构比堆形容词更重要

  • 同一张“春季钢琴海报”，简略写法（3D 卡通、左上标题、右上 2026、中间手托书、书上是北京特色建筑照片）只能得到一般效果。提高质量的写法会先说明这是一张海报及风格，再分别写 背景与装饰、字样、主视觉、整体氛围，并加上提高参数权重的关键词。课上用同一模型对比，结构化后创意明显更好。
  • 课堂在 即梦 上注册试用（不必充值）。讲师记得每天大约有 60 或 80 的免费积分，够当堂测试。可直接复制老师的提示词，例如把“北京”改成“上海”、把“天安门”改成“东方明珠”。这种只改关键信息的做法，课上称为 微调 / 提示词优化。也可以大胆改主题（冬日、万圣节、荒诞风格），不必过于小心翼翼。
  • 测提示词时不要选最强、自带“提示词优化”的模型，否则看不出提示词本身的作用；可选相对更次、但指令遵循更好的版本。模型越新不代表生图一定更好，每个版本下面通常有适用场景说明（如科普教学与营销、滤镜、风格一致性、图文海报与文字准确性等）。课上选用指令响应更强的 Seedream 4.7 来测。效果不达标就反复改、再生成，课上称为 “抽卡”；并提到有一类岗位就是持续调提示词、抽到合适素材。生成后把觉得不错的图发到群里。

五、把原则叠进提示词（以小红书竞品分析为例）

1. 先对结果有预知

  • 从“帮我分析小红书”升级为：说清核心功能、目标用户、主要使用场景，以及解决了用户什么问题；直接出分析结论，不要泛泛介绍公司背景。问之前就应对结果有模糊轮廓：里面大概分哪几个模块。
  • 必须养成的习惯：AI 不是替你直接“拿到”一个结果，而是帮你实现或论证一个你已大致想清楚的结果。重复性、计算性和头脑风暴可以交给它，决策权在自己。把 AI 当成技术助力，而不是能共享处境和情感、替代思考的对象。

2. 设置角色：也可以给自己设角色

  • 常见做法是给 AI 设专家角色（资深设计师、分析师、做了十年的 AI 产品经理）。课上补充：还可以 给自己设角色，例如“我是纯小白 / 我马上要面试，请用口语化方式讲清 Transformer，按输入—处理—输出几块讲”。两者搭配，模型才知道听者水平和目标，输出会明显不同。只问“Transformer 是什么”，容易得到一堆听不懂的术语。

3. 补充上下文，并说明给谁看

  • 要交代当下处境和目的，例如：“我们团队正在做下季度产品规划，需要调研小红书作为核心竞品；这份分析要给产品总监看。” 最终读者 会显著改变口吻和结构——给职场汇报、给 8 岁侄女看、给 80 岁长辈看，不可能一样。这些信息看似多余，却会影响结果。

4. 限制输出格式，提高可读性

  • 内容质量够了之后，再提高可读性：例如功能先用一段话判断，再用表格输出模块、做法、优势、劣势和对我们的机会；该用列表用列表，最后也可打包成 PPT 或 HTML，更便于汇报。

5. Few-shot 与 Zero-shot

  • Few-shot（少样本提示）：给参考示例，让输出更符合预期。昨天生成数据时已经用过（如“反驳性人格”下面跟几条示例）。若只给表头、不给示例，表格里的优劣势可能写成小作文，或只剩“多样化 / 同质化严重”几个字，表格就失去意义。给一条长度和维度都合适的示例即可。
  • Zero-shot 是不给示例。两种都是正式用法，场景不同：需要结果落在可控范围（如必须统一成公司格式）时，适合给示例；偏创意、发散时（如视频脚本要避免“第一句钩子、第二句自我介绍”的同质化），往往不适合给参考，需自行判断。
  • 这些原则来自一线厂商的官方提示词指南（可自行查阅 OpenAI 的提示词原则，条目更多）。不是每次对话都要凑齐。只是想知道“Agent 是什么”“中午吃什么”，一句话说清即可，不必大篇幅写，也浪费 token。基准是：需要明确交付物时（给老板的汇报、PPT、Word、一段精修好的提示词等），才把提示词写完整。

6. 中午练习：把分析做成 HTML

  • 练习：换一个自己熟悉的 App（课上点到汽水音乐、网易云等）做调研分析或展示页。不要再交一篇谁看着都头疼的长文档，最终以 HTML 呈现，类似此前 AI 矩阵提案，便于可视化和长截图。这是当天中午的小作业；一般 12:30 下课，大约有半小时。可用 Grok Bot 或 Box 等工具。
  • 最轻量的做法：复制老师最终版提示词，把“小红书”换成目标 App，再要求做成 HTML。第一版网页往往偏丑、字多，需要继续调风格，这就涉及 Web Design。技巧：到 Pinterest（海外图库，设计参考很多）找喜欢的风格，让模型参照输出。不要安于模型自带的固定模板。

六、把可复用的 User Prompt 写成 System Prompt

  • 上午那套面试话术提示词通用性已经较强：换问题和信息补充即可复用。不必每次重打，也不必只存在备忘录里手动调用，而应 转成 System Prompt，变成固定的可复用设定。之后只需发送补充信息和面试问题；若再把个人档案交给这个 Agent，甚至可以只发面试题。

1. 表头、版本号与“基础技能”

  • 较标准的 System Prompt 表头会记录：你是谁、当前是第几个版本、使用语言，以及一句话描述。其中 版本号最重要。提示词会随模型能力更新而过时：对旧模型很合适的交互规则，换到更强的模型上可能变成限制，反而发挥不出来。提示词不可能一劳永逸，必须持续优化。
  • 因此，提示词微调在 2024、2025 年曾是 AI 产品经理的必备技能，现在已是基础技能（课上类比：必须会的能力，像会 SQL 调优一样）。招聘启事里仍常见“提示词调优 / 优化”。改两三个字就可能影响整条流程；若改完效果变差又找不到改了哪两处，就会很难办，所以必须做 版本管理。
  • 角色、目标、规范限制、工作流程等模块，与写得好的 User Prompt 往往差别不大，主要是人称和视角改成“固定给系统用”的写法。

2. 用 Markdown 写，因为它影响权重

  • 这类提示词底层多用 Markdown：一个 `#` 是一级标题，两个是二级，以此类推；`1. 2. 3.` 是有序清单，`- ` 是无序清单。飞书云文档以及其他常见文稿编辑，底层也是这套语法：行首 `# ` 会变成一级标题，`- ` 变成圆点，`1. ` 变成有序列表。
  • 原因：预训练语料里大量文稿以 Markdown 为主，模型对它的理解更强。比它更“原生”的是代码（课上称为 AI 的母语），但不是人人会写，故退而求其次用 Markdown。语法不必系统学，知道即可；可在浏览器搜索 Markdown，用在线编辑器左右对照（预览标题、目录、图片 `![文案](链接)`、代码块、表格等）。注意 `#` 后面通常要有空格，否则不会变成标题。
  • 不用 Markdown 时，模型读到的是被“拍平”的一段话，没有重点。用标题分级，并用 `加粗`（前后各两个星号）标出关键句（如“包括但不限于风格、排版、字体”），可以提高该段权重，帮助模型排优先级。这会影响模型对指令的遵循，而不仅是排版好看。
  • System Prompt 里角色、目标都可以不写，但工作流（workflow）必须写清：第一步到第 N 步各做什么。要把它设成一台“定时机器”，每次回答前都按同一逻辑走一遍。可以用 Markdown，也可以不用，但流程一定要明白。

3. 各模型的默认文风来自 Meta Prompt

  • 课上用同一句“什么是 RAG”问多个模型：有的爱加粗关键词，有的分段并加分隔线，有的两者都有。这些默认风格很鲜明，所以用 AI 写的笔记有时一眼能看出模型痕迹。用户并没有先设 System Prompt，差异来自发版前包上的 Meta Prompt：除安全限制外，厂商也会写入回复语气和排版习惯。了解各模型特点即可。

七、在公司里写 Agent 的系统提示词

1. Tool List：用工具名调用，不要写 API Key

  • 上班后写 System Prompt，多半是为了搭 Agent。公司里通常有一张 Tool List（可调用工具总表），编排时可从中选用。工程侧负责维护，产品侧按需调用。讲师举例：在昆仑万维做 Agent 矩阵时，表里有图像理解、音频理解、视频理解、超分、图像 / 视频生成等。
  • 例如做一个商品图 Agent：上传咖啡或手机原图，自动抠图并生成多张可视化海报（有的加字、有的不加）。生图能力来自调用已封装的生图工具，而不是在提示词里直接接 API。接 API 需要 API Key；若把 Key 写进系统提示词，风险很大。
  • 课上举了早期 Personal Agent（OpenClaw，俗称“小龙虾”）的教训：有人把账号交给它发帖、点赞、回评论，却被问出 API Key、住址、银行卡和手机号一类信息；其本地权限甚至高于使用者，存在改掉指纹 / 密码、锁死电脑等框架级风险。后来还有线下集中安装又集中卸载的插曲。结论：工具应由工程把各模型 API 封进 Tool，提示词里只写工具名（function name / tool name）。例如：“当用户上传图片后，调用某某工具进行图像理解”，把名称抄进去即可触发；前提是该工具在服务器上处于运行和维护中。调用失败不一定是提示词问题，也可能是工程侧超时或工具掉线，需要协同排查。

2. 案例：一键多尺寸出图 Agent

  • 先看一个相对简单的例子：用户上传一张图（如 4:3），Agent 自动生成 1:1、3:4、16:9、9:16 等尺寸，画面内容不变。配套文档叫 Agent 需求文档，逻辑接近 PRD，但不是同一份东西。传统 PRD 要和加一、设计、工程、算法等多部门一起看；Agent 在用户视角前端往往只是一个输入框，设计介入较少，背后整套流程主要由工程部署。这份文档主要给工程看。今天只拆其中的提示词部分，不现场写完整需求文档。
  • 当时那份系统提示词大约 4987 字（模型能力还弱，基本靠手写）。角色和目标相对常规，重点在 工作流：分多步，步下还有子步骤。
  • 双向引用：给不确定对象起名，方便后文调用，避免反复用自然语言描述还可能说不准。例如把用户上传的原图定义为 `user_image_url`；把多轮对话整理后的目标定义为“用户的真实需求”。命名不一定用英文，但要自己能认得，不要起一堆事后看不懂的名字。
  • 调用 Ask Human 一类工具：用户未上传图片时必须调用，弹出选择或补信息（类似 Codex 等产品里需求不清时让你选 A/B/C）。不必在提示词里描述弹窗长什么样，喊工具名即可触发。若已上传图片并指定投放平台，则进入下一步；只上传图、未指定平台，再询问希望生成哪些比例（可多选）；未选或跳过，则默认生成全比例套装——讲师说这是当时的“小巧思”：不选就一次出多张，并扣积分。
  • 固定回复：需要用户必读或必须统一的话术，用引号把全文钉死，不要让模型每次随机生成。例如有人跟生图 Agent 要视频，应固定说明“当前是图像生成 Agent，生成视频请走其他 Agent”，避免回复失控。
  • 写 Agent 提示词的难点，是尽量穷尽用户情况并给解决方案。不要理想化“宝藏用户”（一次上传图片、说清平台和尺寸）。更常见的是只传图不说话、只说话不传图，或开口就要视频。想不到这些，Agent 就会往不可控的方向走。AI 产品必须给出 兜底方案。用户真正需求往往来自多轮问答的整理，而不是第一句（第一句可能只是 hello）。应用用户所有输入（最初需求 + 后续问答）整理出真实需求，再据此执行。
  • 提示词里用颜色标注过两类名字：一类是自己定义的引用名，一类是公司内部工具名（可能看起来像随机英文，看不懂是正常的）。
  • 当时受模型能力限制，才需要把流程写得这么细；现在用 Codex 或即梦等，多尺寸出图往往一句话就能做。但不能用今天的技术否定 2025 年的工作流。学当时的流程，是因为面试时工作经历往前推一两年，仍可能问到 2024–2025 年的做法。课上还提到：RAG 当年几乎是“无冕之王”，现在不少企业已不用或换成其他形态（转写里的新名称不清晰，不以猜测为准），甚至更新的形态也可能再次过时——技术在迭代，但回溯两年仍要能讲。

3. 提示词“屎山”、质量和稳定性

  • 当晚作业之一是把这份提示词拆开：按自己的理解逐段标注“这段在干什么、为什么这样写”，没有统一答案。从工作流开始会变复杂。前半段（获取需求、询问策略、兜底）可以标为 需求澄清；另有段落同时承担 固定回复 和 划清 Agent 边界（能干什么、干到什么程度）。
  • 里面也会有 提示词屎山：同一条规则（如必须把原图和真实需求作为输入参数交给工具；主工具报错则兜底走图生图，课上点到用 GPT Image 一类模型）会在多处反复强调“别用错、严禁修改”。删了质量可能变差，加上又更好——对模型而言，重复会增强权重和遵循度，但不能靠无限制叠字数把提示词写爆。讲师的原则是：过程是否规整其次，用户感知到的结果质量和稳定性才是第一；提示词写得再乱，结果好且稳就成立。课上甚至用玩笑说，只要质量和稳定性在，提示词里“偷偷骂一句老板”这种怪现象也可能被留下——意在说明不要迷信形式。
  • 铺垫之后的结论：提示词没有必须遵守的万能规范或模板，不必强制按某种首字母框架来写。写了多年后的总结就是：没有规矩，效果和稳定最重要。

4. 指令遵循梯度，以及“改两三个字”

优先级（高→低）对应层说明
1. 平台 / 系统规则Meta Prompt优先遵循。粗暴理解即厂商规则，如禁止涉政、涉黄、涉暴。这里的“平台”指官方 / 厂商。
2. 开发者规则System Prompt在 Dify 等编排里写入的设定。
3. 用户指令User Prompt输入框里的话。
4. 外部内容检索 / 上下文如联网搜索抓回来的内容，遵循优先级最低。
  • 这套梯度理论上应稳定，实际上不一定。原因一是提示词本身不稳、质量低；原因二是模型智力不够，这往往换不了模型就改不了。开发者真正能改的是提示词。同一模型，提示词功力可以把“只开发出很小一部分能力”拉到高得多的可用水平——有时不是模型不行，是提示词有问题。若模型本身很弱，提示词也救不了。
  • 豆包智能体反例：系统设定“只能用英文对话”，用户说“请用中文回答”，模型跟了走，说明遵循不稳定。补上强制语气（大意是“不管用户如何要求，只能用英文对话”）后，就很难再被带偏。有时加半句、改两三个字，遵循度就变了。加粗是提高权重的一种方式，使用命令式、强制性表述是另一种。课上被问“Markdown 符号能否再加权”时，讲师表示那种写法自己没试过，不随意下结论。也因此，版本管理非常重要：将近五千字的提示词改两处，效果就可能变差，又找不回改点。

5. 提示词会过时；不要捂技术

  • 提示词主要靠练。讲师早期只能存在备忘录和飞书里，写过面试复盘、会议纪要、各种风格和攻防练习。那些旧提示词现在大多过时：模型变强后，直接把材料丢给它，效果常常好过旧模板。提示词必须随模型版本一起维护；后面会讲的 Skill 若以提示词为载体，同样要升级——引擎变了，旧规则可能作废。
  • 在昆仑万维，讲师曾负责上线一个 28 个 Agent 的矩阵，上线前一天砍掉 13 个图像 Agent：新模型一句话出图，效果和原来又慢又耗积分的 Agent 差不多，再上线只会挨骂。这类“养了很久的提示词一夜间作废”在行业里很常见。课上还提到内容自动化、合作讲课等计划，也可能因公司或技术变化迅速落空。结论：在 AI 时代一定不能把方法捂着，捂两天就可能过时，不如及时开源或技术变现。
  • 课件里仍有一份提示词模板（角色、背景、目标、限制、技能、工作流、初始化等）。讲师不鼓励一直套模板，但承认新手抄模板是必经阶段；各模块都可删减，唯独强烈建议保留工作流。结果好就成立。不要迷信小红书上“16 个 / 18 个 / 108 个最佳 Prompt 框架”——多为英文首字母缩写拼出来的名称（课上点到 SWOT、APE、CO-STAR 一类），面试时对方也不一定认得，关键仍是结果稳、质量好。其中讲技法、讲迭代的早期文章可以看。

6. 建议知道的人与资料

  • 结构化提示词要记住两个人。第一是 吴恩达：与 OpenAI 合作推出过相关课程，B 站能看到全程，对提示词结构化有奠基贡献。第二是 李继刚：把这一思维发扬开去，分享过不少方法，曾被人称为“提示词之神”。可关注其公众号，但应翻 2024–2025 年能直接拿来用的文章；讲师觉得近期偏“论道、人性、文字真谛”的内容营养不足，可能是层次未到，也可先不看。
  • 第三个信息源，课上指向 飞书上的相关资料（里面有大量提示词文章，并用分隔符组织内容，本质仍接近 Markdown 再加点代码记号）。李继刚早期还用 Lisp（很老的编程语言）写提示词，表达可以很精确，但难学。讲师的态度是：现在学会 Markdown 已够用，不必为了炫技去学这类语言；不少方法是早期研究者趟出来的，现在是既得利益者，有空可以回看当时的思想碰撞。

八、提示词的版本管理

  • 方法一（讲师上班常用）：办公工具是飞书，就在飞书里做版本管理，版本号以日期为样本。局限是同一天可能改很多次；细到小时又嫌麻烦。这是明确痛点，市面上好用的提示词版本管理工具很少。
  • 方法二：每次改动记入改动表，写清改了什么。进度默认可以是“正在修改”或“待推上线”。工程 / 前后端进来，看到“待推”就上线，看到“正在修改”就先不动。多部门协作时很高效。讲师在公司内部搭过这张表，后来昆仑侧的 Agent 编排基本沿用；同时维护很多 Agent 时，没有表会记不住。
  • 方法三：体验字节的 Prompt Police（课上点名的产品）。它带版本管理，但收费贵、也难用，UI 交互讲师不太习惯。可以去试用，看看有没有产品idea。除此之外，讲师说自己还没看到特别好用的版本管理工具，日常仍主要用飞书。

九、知识库与 RAG：先会用，细节以后展开

  • 课上在 Dify 里演示了知识库切分，并说明 RAG 会另作专题，此处只要知道做什么、怎么用、起什么作用。
  • 切块要适中。一篇长文若直接整篇塞进模型，既浪费 token，也容易把上下文冲爆，所以要切分；问到哪一段相关，再把那一段召回。切得太碎（一句一段）时，召回的可能是孤零零的标题或单句，拼不出逻辑，质量会差；切得太长（例如五千字只切成两段）也不行。可调“分段最大长度”，并用 分段标识符 控制在何处下刀——默认遇到空格就切，若文中空格很多就会切得过碎；可改成“句号结尾后的空格”再切，块会更完整。来回调参数，看右侧预览是否合适再保存。
  • 创建知识库时会用到两个与大语言模型不同的模型：Embedding（把自然语言转成机器可计算的向量）和 Rerank（重排序）。流程是：用户提问后，先在库里找出相关片段召回；稍有相关的都可能被拽回来，信息会很杂。Rerank 按与问题的相关程度再排一次，只把前 3～5 条交给大模型作答。课上类比：投递来的简历很多，HR 把更符合要求的留下来约面，其余淘汰。
  • 只接入 DeepSeek 时，往往 只有大语言模型，没有 Embedding / Rerank，知识库用不起来，需要再接同时提供这类模型的服务（课上点名的具体接入方转写不清，以当时演示为准）。切换模型时，右上角若弹出参数被移除的黄框，是因为不同模型支持的参数不同，属于兼容处理，不必紧张。
  • 排查顺序：先做知识库的 召回测试，看能否把库里的对应片段拽出来。召回正常而对话仍答不对，再去查大模型或策略（例如是否强制在回答时调用该知识库）。挂上档案或笔记后，即使不在对话里重说一遍，按理也应能读到库里的信息。用法不限于个人档案，也可以把课堂笔记上传进去。
  • 发布后的用户页往往只剩一个输入框，可在管理里配置 开场白（进来先自动说一段话，如 Grok Bot 登录后的问候）和 下一步问题建议。语音转文字、文字转语音，讲师觉得该平台做得一般，可跳过；标注回复、内容审查等可自行试。顺带复习模型参数：温度可调；鼠标悬停能看到模型类别（如 Chat）、上下文长度（课上举例约 1040K）以及是否多模态（能否识图）。课上还演示了较新的 Gemini 型号，可看文档、视频、语音和图片，属于全模态，选项会相应变多。不同模型支持的能力不一样。

十、课堂命题、作业、辩论与课程延期

1. 当堂命题：把笔记用起来

  • 命题是做一个能把已有 笔记 用起来的 Agent，可结合变量和知识库。讲师举的方向包括：讲解笔记里出现过的技术名词；根据笔记出面试题并生成对应话术；基于笔记做思路延展或相关信息检索（后者可能要调工具，当堂可不做）。做成陪伴成长，还是做成提问 / 问答，取决于提示词怎么写。
  • 不要一上来就只在 Dify 里硬写。应先和自己的主力 AI（Codex 或 Grok Bot）把思路和方案聊清楚，再让它帮忙写提示词，最后才到 Dify 里测试。Dify 对同学而言是实验场，不是主战场；主战场在自己的主力 AI 上。每人应有一个主力工具，逮着一个持续用，让它习惯自己的交接方式；换来换去，语料会分散，不会越用越好用。课上没做完的，就是当天晚上的作业。

2. 当晚要交 / 要做的四件事

  • ① Dify Web 应用链接：编排并发布后，打开外部应用，把这个用户视角的链接放在笔记最上面。老师访问该链接即可体验产品。这是第一项。
  • ② 课堂笔记。
  • ③ 拆解老师提供的系统提示词：打开文档后用“创建副本”，只在自己的副本里挂评论，不要直接在老师的原文档里评论（否则许多人同时批注会把原文档搅乱）。按段分析写它的目的，从工作流、需求澄清、固定回复、边界等角度理解即可。先拆单 Agent；课上预告，后面还会碰到多 Agent 并行，提示词会更长（课上展示过另一组各数千字、合计支撑一个名为 product demo image 一类 Agent 的例子），今晚先不要一上来就看最重的。
  • ④ 准备次日（周五）上午的辩论——固定保留节目，不算一般书面作业，但全班都要准备。

3. 辩论安排（2026-11-27 周五上午）

  • 辩题：在 AI 时代，我们必须要 AI 化转型。一边正方（赞成）、一边反方（反对）。下课后面对面建群，两边各设一名临时大队长；形式为 8 对 8，队长必须上场，其余 7 人向队长报名。次日上午 10:00，两边队长把一辩到八辩名单发给老师。
  • 除队长外应有 7 人报名。若某边缺人：缺 1 个则之后作业加倍，缺 2 个三倍，缺 3 个四倍，按缺的人数往上加。第一、二排男生走之前把桌子摆成对辩布局（前两排桌子横过来，每边约 8 人）；其余座位往后推。没上场的是后备军，第二周周五上午还有场，人员尽量不重复，后备军也要参与投票。另有竞赛规则（含禁言等，转写未展开全部细则），当晚会发到群里，需仔细研读，也可利用规则应对；可以换人。讲师做主持，类比狼人杀。
  • 上场 不能看手机和电脑照着读，否则就失去辩论意义；不能人身攻击、不能骂人。许多人可能没怎么辩过，这只是模拟。目的是练表达：将来在公司往往是一人应对设计、前后端、运营运维、开发、QA、加一加二、业务、CEO 等，作为项目负责人既要向上要资源、向下管理，也要和兄弟部门友好协同，说话很关键。课程会保留大量辩论和提案上台的机会，公司里未必再有这样的练习场。双方当晚就要讨论观点、上场顺序和发言流程。

4. API / Tool / MCP 推迟

  • API、Tool、MCP 原计划当天下午讲，但这些内容与 Agent 隔离不开，要讲就得连着讲，因此 往后放到与 Agent 一起。当天课程讲到此处结束，留下时间在教室完成作业讨论和临时组队，避免住得远的同学回家后再协同（课上提到有人路程可能要一个多小时）。
